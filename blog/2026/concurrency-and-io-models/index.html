并发、竞争与 I/O 模型详解

Created on June 30, 2026

2026   ·   Linux   并发   I/O模型   驱动开发   ·   Linux学习

在操作系统（尤其是嵌入式 Linux 驱动开发）中，并发与竞争以及I/O 模型是处理多任务和底层数据交互的核心机制。 核心要点概括：

  • 并发与竞争关注的是“多个任务抢占同一资源”的问题，解决的是数据安全和状态一致性。
  • I/O 模型关注的是“任务如何等待和处理数据”的问题，解决的是 CPU 利用率和系统的吞吐量。
  • 两者的不同在于：前者是内部资源的互斥与同步，后者是任务与外部设备（或网络）之间的数据交互方式。

一、 并发与竞争（Concurrency and Competition）

1. 各种操作（常见机制）

为了防止多个线程、中断或 CPU 核心同时访问共享资源（临界区），内核提供了以下解决工具：

  • 原子操作（Atomic Operations）： 依赖硬件指令保证操作的不可分割（如“读-改-写”一步到位），适用于简单的计数器。
  • 自旋锁（Spinlock）： 线程在获取不到锁时不会休眠，而是在原地死循环（自旋）等待。适用于锁持有时间极短、且不能休眠的上下文（如中断处理程序）。
  • 信号量（Semaphore）： 允许指定数量的线程同时访问资源。获取不到锁时，线程会进入休眠。适用于锁持有时间较长的场景。
  • 互斥体（Mutex）： 专为互斥设计的信号量（计数器为1）。具有优先级继承机制，防止优先级翻转。

2. 解决什么问题

解决临界区数据被破坏（Race Conditions）的问题。当多个 CPU 核心（SMP）、中断服务程序、或者抢占式内核的多个线程同时修改同一个全局变量或硬件寄存器时，会导致计算结果随机、硬件状态异常等问题。

二、 I/O 模型（I/O Models）

1. 各种 I/O 模型

当应用层需要从底层驱动或网络读取数据时，主要有以下五种模型：

  • 阻塞 I/O（Blocking I/O）： 应用层调用 read，如果数据没准备好，当前线程挂起（休眠），直到数据准备就绪并复制到用户空间才返回。
  • 非阻塞 I/O（Non-blocking I/O）： 如果数据没准备好，驱动立即返回一个错误码（如 -EAGAIN）。应用层需要通过轮询（Polling）不断尝试读取。
  • I/O 多路复用（I/O Multiplexing）： 使用 select、poll 或 epoll。一个线程同时监听多个文件描述符（FD）。当任何一个 FD 就绪时，再调用 read 读数据。
  • 信号驱动 I/O（Signal-driven I/O）： 内核在数据准备就绪时，向应用层发送 SIGIO 信号，应用层在信号处理函数中异步读取数据。
  • 异步 I/O（Asynchronous I/O - AIO）： 应用层发起 aio_read 后立即干别的事。内核负责等待数据、并将数据复制到用户缓冲区，全部完成后再通知应用层。

2. 解决什么问题

解决“CPU 速度与低速外设/网络速度不匹配”的问题。它决定了当硬件数据未就绪（如串口还没收到数据、网络没有报文）时，CPU 应该如何等待，以最大化系统资源的利用率。

三、 两者的本质不同

我们可以通过一张对比表来直观看出两者的差异：

维度 并发与竞争机制 I/O 模型
关注核心 保护内部共享资源（变量、结构体、硬件寄存器）。 规范数据流向（硬件 → 内核空间 → 用户空间）。
解决目标 数据安全性：防止多任务同时写数据导致状态混乱。 系统高效性：决定任务在等待硬件数据时是否让出 CPU。
作用维度 横向（同级）：线程与线程、线程与中断、CPU 核心之间。 纵向（跨层）：应用层、内核驱动层、硬件设备之间。
典型代表 自旋锁、互斥体、原子变量。 阻塞、非阻塞、epoll 多路复用。

一句话总结两者的联动关系： 在开发驱动时，你可能会用 I/O 模型（如阻塞 I/O）让没有数据的用户线程在队列中休眠；而为了安全地操作这个“等待队列”，你内部必须使用自旋锁（并发控制）来防止多个 CPU 核心同时修改队列结构。
